# 42.21 upgrade impact

**Recommendation: proceed with an isolated port.** The inspected changes do not establish
a need to replace the architecture, C++ planner, protobuf transport or ordinary Lua client
approach. They do establish that the current Java agent cannot run unchanged. This is a
completed acquisition and impact assessment, not a completed port or modded playtest.

The existing 42.20.4 deployment remains the default. No gameplay source, compatibility
guard, installed mod, existing save or distribution artifact was changed for this study.
The `.160` production deployment was untouched.

## Transformer audit and guard coverage

Of the current **63 guarded classes**, **31 changed**, 32 are byte-identical and none are
missing. A changed class hash is a review obligation, not evidence of a broken feature.

The original transformer was applied to both JARs in a standalone inspection helper,
without bypassing premain or injecting into a game session. All 17 transformed candidate
classes passed Java ClassFile structural verification. However, the audit found 44 distinct
method/helper-call entries on the baseline and only 41 on the candidate. Three entries
disappeared, representing six old call sites:

- Four combat relay calls in `CombatManager.attackCollisionCheck`.
- One combat relay call in the old `CombatManager.processTreeHit` signature.
- One factory guard call in `VirtualZombieManager.createRealZombieAlways`.

The new combat code collects hits per target and sends the grouped result later. The port
must audit that control flow, not try to reproduce the old count mechanically. Structural
verification does not prove correct execution, collision or replication.

`NetworkPlayerVariables`, its `Flags`, `PlayerPacket` and `ZombiePopulationManager` are
outside the present 63-class guard. Add reviewed coverage for these dependencies during
the port, together with an explicit hook inventory that fails if an intended interception
disappears. Do not merely replace the existing hash list with candidate hashes.

Evidence: `guard-class-diff.json`, `other-class-diff.json`, `hook-audit-old.tsv`,
`hook-audit-new.tsv`, `hook-diff.json`, and `api-old.txt` / `api-new.txt`.

## Semantic risks needing native tests

**Zombie lifecycle and persistence are the largest uncertainty.** Candidate bytecode adds
persistent population IDs, native registration/release and stale-record rejection.
The new factory registers a zombie after world insertion. Native `IsoZombie.removeFromWorld`
releases that population registration and clears the ID; corpse reanimation registers
its new zombie. Preserve those engine calls and verify them rather than replacing them
with field edits. Removal, death, chunk unload/reload and reanimation must each account
for both network presence and population identity.

Our current pooled civilian bodies are `IsoPlayer` objects. The new zombie ID contract
directly concerns native hunters, reanimated aftermath and the older zombie-backed
adapter; it does not mean every civilian pool body needs a zombie ID. Civilian death and
reuse still cross that contract through their corpse/reanimated replacement.

**Movement and vehicles need independent replay.** Of 56 compared native libraries,
49 are unchanged and seven changed. Both Bullet libraries are identical, including the
guarded server library, but `libPZPathFind64.so`, `libPZPopMan64.so` and RakNet changed.
Java `PathFindBehavior2`, `NetworkPlayerAI`, `BaseVehicle`, `CarController`, vehicle packets,
animation and character classes also changed. An unchanged physics library therefore
does not qualify steering, interpolation, gait or obstacle handling.

Upstream notes report work on zombie duplication/chunk returns, networking and vehicle
presentation, player pathfinding, and object reuse. They also remove vehicle collision
from player-built campfires: a campfire-based crash expectation must change, whereas a
verified solid-object crash remains useful coverage. These are upstream behavior changes,
not observed AKR regressions. See the [official patch notes](https://theindiestone.com/forums/topic/101693-4221-patch-notes/).

The C++ worker and our protobuf schema do not link the game engine. Existing component
and transport tests pass; no protocol redesign is indicated by this assessment. Their
end-to-end integration still depends on the ported Java execution and feedback path.

## Port sequence and effort estimate

Keep 42.20.4 available throughout. Build a separate candidate profile/artifact directory
and fresh worlds; don't retarget the default launcher or overwrite the existing dist.

1. Freeze candidate game/dependency identities and explicit build paths. Add reviewed
   class/native dependency coverage and a required-hook inventory. Test rejection of
   mismatched builds and absent hook locations.
2. Port movement flags and combat hit lists together with focused tests for native
   serialization, stock damage exactly once, misses, stale targets, interruptions and
   normal player combat outside the managed scope. Fix the Lua door fixture.
3. Port the factory guard and validate calm-world suppression, explicit permitted spawns,
   registration, cleanup, corpse/reanimation and exact Actor reuse in a disposable native
   fixture. Requalify Observer and the chosen upstream dependency separately.
4. Run the existing headless suite, then the maintained one-seat watched batch in stages:
   WALK/RUN and doors; one then four combat encounters; repeated fatal lifecycle/reuse;
   routine and chase; vehicle regressions after updating their spectator/fixture adapter.
   Preserve placement, daylight, protection, loaded 9mm, announcements and cleanup rules.
5. Measure performance and compare two real clients before claiming multiplayer
   qualification. Promote the candidate only after its explicitly scoped gates pass.

Planning estimate, not a delivery promise; assumes no new engine-level blocker:

| Work | Focused engineering effort |
| --- | --- |
| Candidate build/profile and guard/hook coverage | 4–8 hours |
| Movement flag port and targeted tests | 2–4 hours |
| Combat list relay, effects and regression tests | 4–10 hours |
| Population, cleanup and fatal lifecycle qualification | 4–8 hours |
| Lua, Bandits and Observer compatibility | 2–4 hours |
| Regression harness updates and first regression/triage pass | 8–16 hours |
| **Total initial port and qualification work** | **24–50 hours, roughly 3–7 focused working days** |

Two-client coordination, broader mod compatibility, long stress runs, existing defects
and any unexpected native-engine issue can extend this. Merely reaching a successful
compile is a much smaller milestone and must not be reported as a working upgrade.

The baseline is not an entirely green visual suite: the 2026-09-29 four-Actor run failed
replica divergence, the chase did not qualify, and five vehicle cases were blocked by
the old harness. Keep those results as separate known issues; use the same reproductions
on both builds before attributing a failure to 42.21. The neighborhood feature task
remains pending; this study does not complete it or authorize ambient rollout.
